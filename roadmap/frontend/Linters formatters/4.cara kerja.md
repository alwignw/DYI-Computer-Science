### Alur Langkah demi Langkah (*Pipeline*)

Ketika Anda menjalankan linter/formatter (misalnya saat menekan `Ctrl + S` di IDE atau running perintah CLI), proses berikut terjadi dalam milidetik:

```text
[ File Kode (.js, .py, .go) ]
               │
               ▼
   1. Lexing / Tokenization
   (Mengubah teks mentah menjadi token-token individual)
               │
               ▼
        2. Parsing (AST)
   (Menyusun token menjadi pohon struktur hirarkis)
               │
               ▼
      3. AST Traversal & Rules
   (Linter/Formatter "berjalan" menelusuri tiap node pada AST)
               │
        ┌──────┴──────┐
        ▼             ▼
   Linter Checks   Formatter Layout Engine
   (Evaluasi rule) (Hitung ulang spasi & margin)
        │             │
        └──────┬──────┘
               ▼
     4. Report / Auto-Fix
   (Tampilkan error ke terminal/editor ATAU tulis ulang file)

```

1. **Lexing / Tokenization:** Teks kode dipecah menjadi *token* dasar. Teks `const a = 1;` dipecah menjadi `[KEYWORD: const]`, `[IDENTIFIER: a]`, `[OPERATOR: =]`, `[NUMBER: 1]`, `[PUNCTUATION: ;]`.
2. **Parsing:** Token-token tersebut disusun membentuk **AST**.
3. **AST Traversal & Evaluation:**
* **Linter:** Menggunakan pola *Visitor Pattern*. Saat mengunjungi node `VariableDeclaration`, linter mengeksekusi fungsi pemeriksaan untuk aturan seperti `no-var` atau `no-unused-vars`.
* **Formatter:** Mengabaikan arti token, hanya mengukur panjang karakter tiap node, kedalaman indentasi, dan menerapkan aturan layout (*print width*, *tab width*).


4. **Report / Auto-Fix:**
* Jika ada kesalahan yang bisa diperbaiki otomatis (misal: merubah `var` ke `const` atau menambah titik koma), file langsung ditulis ulang (*auto-fix*).
* Jika tidak bisa (misal: fungsi butuh argumen yang hilang), linter mencetak pesan kesalahan berisi baris dan kolom lokasi bug.

### Contoh Sederhana (Sebelum & Sesudah)

Misalkan Anda memiliki kode JavaScript berikut:

#### 1. Kode Mentah (Sebelum Diproses)

```javascript
var age = "25";
if(age == 25){
console.log('User is adult')
}
var unusedVar = 100;

```

#### 2. Apa yang Dilakukan Formatter (Prettier)

Formatter merapikan tampilan visual tanpa merubah variabel/operator:

```javascript
var age = "25";
if (age == 25) {
  console.log("User is adult");
}
var unusedVar = 100;

```

*(Indensasi diperbaiki, spasi di dalam `if` ditambahkan, titik koma dilengkapi).*

#### 3. Apa yang Dilakukan Linter (ESLint dengan Auto-Fix)

Linter memeriksa aturan logika dan keamanan:

```javascript
// ERROR: 'unusedVar' is defined but never used (no-unused-vars)
// WARNING: Expected '===' and instead saw '==' (eqeqeq)

const age = "25"; // 'var' diubah otomatis menjadi 'const' (prefer-const)
if (age === 25) { // '==' diubah otomatis menjadi '==='
  console.log("User is adult");
}

```

### Contoh Dunia Nyata: Alur Pengembangan Tim (*Developer Workflow*)

Dalam skala proyek profesional, Linter & Formatter diintegrasikan dalam 3 lapisan pertahanan (*Layers of Defense*):

```text
[ Developer Environment ]
  │
  ├─ Layer 1: Code Editor (VS Code)
  │    └─ Saat `Save`: Auto-format & tampilkan garis merah wavy di bawah kode yang error.
  │
  ├─ Layer 2: Git Pre-commit Hook (Husky + lint-staged)
  │    └─ Saat `git commit`: Otomatis jalankan linting hanyak pada file yang diubah.
  │       Commit DITOLAK jika ada error linter yang belum diperbaiki.
  │
  └─ Layer 3: CI/CD Pipeline (GitHub Actions / GitLab CI)
       └─ Saat `Pull Request`: Server menjalankan `npm run lint`.
          PR TIDAK BISA DI-MERGE jika status check gagal (mencegah kode rusak masuk ke branch 'main').

```
