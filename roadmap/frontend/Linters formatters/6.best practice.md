## 6. Best Practice

Di industri software engineering, standar penggunaan linter dan formatter sudah sangat terpolakan. Mengikuti *best practice* ini akan menyelamatkan tim Anda dari pusing konfigurasi dan debat gaya penulisan (*flame wars*).

---

### Cara yang Umum Digunakan di Industri & Alasannya

#### 1. Terapkan *Strict Separation of Concerns*

* **Aturan:** Serahkan **100% tata letak visual** ke Formatter (seperti Prettier, Black, atau GoFmt), dan serahkan **100% analisis kualitas kode** ke Linter (seperti ESLint, Ruff, atau Clippy).
* **Alasan:** Jika Linter dipaksa mengatur spasi dan titik koma, konfigurasi akan menjadi sangat rumit, melambat, dan sering bertabrakan dengan Formatter. Gunakan plugin penyelarasi seperti `eslint-config-prettier` untuk mematikan aturan visual pada Linter.

#### 2. Gunakan *Presets / Shared Configs* Komunitas

* **Aturan:** Jangan buat puluhan aturan Linter dari nol secara manual. Gunakan preset rekomendasi resmi atau standar industri, misalnya `eslint:recommended`, `plugin:@typescript-eslint/recommended`, atau `airbnb-base`.
* **Alasan:** Menghemat waktu berjam-jam dan memanfaatkan ribuan jam pengalaman komunitas yang sudah menguji aturan-aturan tersebut di proyek skala besar.

#### 3. Terapkan Strategi 3 Layer (*Editor, Git Hook, CI/CD*)

* **Aturan:**
1. **Editor:** Aktifkan *Format on Save* di IDE masing-masing dev.
2. **Pre-commit Hook:** Gunakan tool seperti **Husky** + **lint-staged** untuk menjalankan Linter/Formatter *hanya* pada file yang di-`git add`.
3. **CI Pipeline:** Jalankan `prettier --check` dan `eslint` di GitHub Actions/GitLab CI.


* **Alasan:**
* Editor memberi *instant feedback* saat mengetik.
* Pre-commit mencegah kode kotor masuk ke Git history local (dan sangat cepat karena hanya mengecek file tersimpan/staged).
* CI Pipeline menjadi benteng terakhir yang tidak bisa di-bypass oleh siapapun.



#### 4. Anggap *Warnings* sebagai *Errors* di CI Pipeline

* **Aturan:** Di lingkungan CI/CD, jalankan linter dengan flag ketat, misalnya `eslint . --max-warnings 0`.
* **Alasan:** *Warning* yang dibiarkan lama-kelamaan akan menumpuk hingga ratusan (*warning fatigue*). Ketika *warning* terlalu banyak, developer akan mulai mengabaikannya, termasuk *warning* yang sebenarnya berbahaya.

#### 5. Abaikan Kode *Generated* & *Build Artifacts*

* **Aturan:** Selalu tambahkan file ignore (`.prettierignore`, `.eslintignore`, atau section `ignorePatterns`) untuk folder seperti `/dist`, `/build`, `coverage/`, `node_modules/`, serta file hasil generate (seperti GraphQL/Protobuf Types).
* **Alasan:** Mencegah pemborosan daya komputasi CPU dan menghindari *false positive error* pada kode yang dieksekusi oleh mesin, bukan ditulis manusia.
