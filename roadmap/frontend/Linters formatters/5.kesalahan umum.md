## 5. Kesalahan Umum

Banyak *developer*—bahkan yang sudah berpengalaman—sering kali mengalami frustrasi saat bekerja dengan *linter* dan *formatter*. Sebagian besar masalah tersebut bersumber dari beberapa miskonsepsi dasar berikut:

---

### Miskonseptic yang Sering Terjadi

#### 1. Menganggap Linter dan Formatter Adalah Hal yang Sama

* **Miskonsepsi:** "Saya sudah pakai Prettier, jadi tidak perlu ESLint lagi" (atau sebaliknya).
* **Fakta:** Prettier tidak akan memberitahu Anda jika ada variabel yang *unused* atau *promise* yang tidak di-`await`. ESLint bisa mengatur format, tetapi jauh lebih lambat dan tidak seandal Prettier dalam menangani *edge case* tata letak visual.

#### 2. Mengira "Linter Lolos = Kode Bebas Bug"

* **Miskonsepsi:** Jika `npm run lint` hijau (tidak ada error), berarti aplikasi dijamin berjalan lancar.
* **Fakta:** Linter hanya mengecek **sintaksis dan semantik dasar**, bukan **logika bisnis**. Kode yang *lint-free* tetap bisa memiliki bug logika seperti salah menghitung rumus diskon atau salah memanggil ID user.

---

### Hal yang Sering Membuat Pemula Bingung

#### 1. Perang Aturan (*Rule Conflicts*) Antara Linter & Formatter

* **Gejala:** Anda menekan `Ctrl + S`, Prettier mengubah tanda petik menjadi *double quotes* (`" "`), tetapi ESLint langsung memberi garis merah karena aturan project mewajibkan *single quotes* (`' '`). Editor Anda seperti "berkelahi" dengan dirinya sendiri.
* **Penyebab:** Linter dikonfigurasi untuk menangani aturan *formatting* visual yang bertabrakan dengan aturan Formatter.
* **Solusi Industri:** Matikan semua aturan *formatting* di Linter dan serahkan sepenuhnya ke Formatter (misal: menggunakan plugin `eslint-config-prettier`).

#### 2. Terlalu Murah Hati Menggunakan Inline Suppression

* **Gejala:** Menambahkan `// eslint-disable-next-line` setiap kali Linter mengeluarkan pesan *error*.
* **Penyebab:** Diabaikan karena malas memperbaiki pesan error yang muncul.
* **Akibat:** Ini sama saja dengan mematikan alarm kebakaran saat ada asap. *Inline suppression* seharusnya hanya digunakan pada *edge case* yang sangat spesifik dan disertai alasan yang jelas di komentar.

```javascript
// BAD: Menyapu bug di bawah karpet
// eslint-disable-next-line react-hooks/exhaustive-deps
useEffect(() => {
  fetchData(userId);
}, []); // `userId` hilang dari dependency list, berpotensi memicu stale data bug!

// GOOD: Perbaiki akar masalahnya
useEffect(() => {
  fetchData(userId);
}, [userId]);

```

#### 3. Lupa Membuat File `.ignore` (`.eslintignore` / `.prettierignore`)

* **Gejala:** IDE/CLI menjadi sangat lambat saat menjalankan linting, atau muncul ribuan error dari folder `node_modules`, `dist`, atau `.next`.
* **Penyebab:** Linter mencoba menganalisis jutaan baris kode pustaka pihak ketiga atau berkas *bundle* hasil *build*.
